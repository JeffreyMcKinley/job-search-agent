# Setup

Gets a fresh checkout to the point where `/apply-prep` can run. Most of the
candidate data comes from the `proficiently` plugin's own onboarding. This skill
runs that first, then does the one step proficiently does not: turning its work
history profile into `.personal/candidate-facts.md`.

Paths below use `DATA_DIR` for the proficiently data directory (`data_dir` in
`~/.jobtrackeragent/config.toml`, default `~/.proficiently`), `FACTS` for
`D:\Code\HelperAgents\.personal\candidate-facts.md`, and `PY` for
`D:\Code\HelperAgents\venv\Scripts\python.exe`.

If `$ARGUMENTS` is `facts`, check that Step 1's inputs exist, then go to Step 3.

---

## Step 1: Proficiently onboarding

Check that each of these exists and holds real content, not an unfilled
template:

- a resume in `DATA_DIR/resume/`
- `DATA_DIR/preferences.md`
- `DATA_DIR/profile.md`, with a `## Role: <Title> at <Company>` section for
  every role on the master resume

If any is missing, invoke `/proficiently:setup` with the Skill tool and let it
finish. It creates only the missing pieces. If only the profile is missing or
thin, invoke it with the argument `interview`.

The facts file depends on proficiently's interview having collected
**quantified** accomplishments. If no software role in `profile.md` has a
Key Accomplishment or Metrics Bank row with a real number, run
`/proficiently:setup interview` again and ask for numbers on those roles before
continuing.

## Step 2: Repo configuration

Check that `~/.jobtrackeragent/config.toml` and `profile.toml` exist. If either is
missing, stop and point the user to the "Configuration" section of the repo
README. `profile.toml` must name the master resume (`[resume] master_filename`);
Step 3 reads that file.

## Step 3: Derive the facts file

Read two sources:

1. **The master resume**: `DATA_DIR/resume/<master_filename>`. For a `.docx`,
   extract the text with
   `PY -c "import sys,zipfile,re;x=zipfile.ZipFile(sys.argv[1]).read('word/document.xml').decode();print(re.sub(r'<[^>]+>','',x.replace('</w:p>','\n')))" "<path>"`.
2. **The work history profile**: `DATA_DIR/profile.md`.

Build the three sections from them:

| Section | Source | Rule |
|---|---|---|
| Software engineering roles | Master resume's experience section | Every employer listed there, named exactly as the resume names it. |
| Operations roles | `profile.md` `## Role:` sections | Roles in the profile that are **not** on the master resume, plus any non-software role on it. Add what the job was in parentheses, taken from the role title. |
| Operations-only skills | `profile.md` (the operations role sections, and any non-software skills section) | Skills that appear only under operations roles. A skill that a software role also supports does not belong here. |
| Headline results | `profile.md` Key Accomplishments and Metrics Bank, **software roles only** | Three to five, each carrying a concrete number. Write each as a short noun phrase in the form "the $X/month billing platform", not a sentence. Prefer results that also appear as bullets on the master resume. |

If a role's classification is unclear, such as a technical role with no
software engineering in it, ask the user. Do not guess.

## Step 4: Confirm and write

Show the user the draft. If `FACTS` already exists, show what changes. Write it
only after they confirm, in exactly this shape (apply-prep refers to the section
headings by name):

```markdown
# Candidate facts

Private. Gitignored. Generated by /setup from the proficiently profile and the
master resume; re-run /setup facts after either changes.

## Software engineering roles

The roles a software engineering resume's experience section may draw from:

- **<Employer>**

## Operations roles (career-pivot only)

Pre-software roles, kept for applications to non-software roles such as
procurement or purchasing. Never on a software engineering resume.

- **<Employer>** (<what the job was>)

Skills that come only from these roles, and so stay off a software resume:
<skill>, <skill>.

## Headline results

The strongest quantified work, used to lead screening answers and to make a
domain point without listing an operations role:

- the <result>
```

Leave the operations section's list empty, but keep its heading, if there are
no operations roles.

Then run `git -C D:\Code\HelperAgents check-ignore -q .personal/candidate-facts.md`.
A non-zero exit means `.personal/` has fallen out of `.gitignore`. Stop and tell
the user, because the next commit would publish the file.

## Step 5: Summary

Report what Step 1 created or found, and list the roles and results now in
`FACTS`. Finish with the skills that are now usable: `/job-tracker`,
`/apply-prep <url>`, `/mass-apply`.
